## §G
Flask API: relay frontend ↔ oSPARC (functions, jobs, collections, studies), generate samples (LHS / grid / single), run Dakota meta-modeling (SUMO surrogate, UQ propagation, MOGA optimization), persist state text files. Serve under `/flask/*`, port 5000.

## §C
- Python 3.11, `flask==3.1.1`, `flask-cors==6.0.0`, `gevent==25.5.1`
- run: dev `uv run python -m flask run` (entrypoint.sh), prod `uvx gunicorn main:app` (`main:app = create_flask_app()`)
- oSPARC client `osparc==0.8.3.post0.dev30`; Dakota `itis-dakota==1.5.9`
- numerics: `numpy==2.2.6`, `pandas==2.2.3`, `scipy==1.15.3`, `scikit-learn==1.6.1`
- `mmux_flaskapi.dakota` subpackage (inlined, own module namespace) → Dakota conf generation + result evaluation + `lhs()` — was vendored `mmux_python` dep, ported in-repo (§T15)
- requests accept camelCase|snake_case (pydantic `populate_by_name`); responses camelCase
- `DataPreprocessor` maps orig var names → `x1..xn`,`y1..yn` for Dakota, inverse on response
- ≥5 completed jobs required for any surrogate/UQ/MOGA endpoint
- ruff line-length 100, select E/F/I/UP; pytest markers slow/integration/unit; coverage aim ≥70% on modified code (soft)
- naming: Classes PascalCase | funcs/methods snake_case | constants CONSTANT_CASE | private `_`prefix
- type hints + PEP257/NumPy docstrings on public APIs; raise ValueError/RuntimeError w/ descriptive msg; log via `utils/logger.py`

V30: uncertainty-availability (`{output}_std_hat`) checks ∀ run against the surrogate's own computed `results` dict (post-`evaluate_sumo()`), never against raw `function_jobs[].outputs` — raw job outputs hold only real simulation values, `_std_hat` does not and never will exist there (closes B12)
V31: strict remote oSPARC endpoints ! call the configured SDK surface and propagate downstream `OsparcApiException` status/body; connectivity probing is confined to optional local-fallback helpers (`get_osparc_api_if_connected`), ⊥ preflight network test in `get_osparc_api` that masks endpoint-specific SDK errors (B14)
V32: `POST /flask/dakota/compute_sobol_indices` builds a surrogate from completed jobs via `evaluate_sumo()`, then computes Sobol' indices directly in Python: generate Saltelli A/B/AB sample matrices locally (honouring per-input distributions via `scipy.stats.rv_continuous.ppf`; `constant`-distribution vars excluded from sampling, returned as `{main:0.0,total:0.0}`), evaluate all samples in ONE batch through `evaluate_sumo()` (surrogate-only, Dakota now ⊥ run `variance_based_decomp` itself), then apply `scipy.stats.sobol_indices` for first-order + total-order indices (single-varying-variable case bypasses scipy, computed via direct Saltelli 2010 covariance formulas since scipy's array-squeeze crashes at d=1) + a closed-form second-order (pairwise interaction) estimator (Jansen/Saltelli 2010; reuses f_A/f_B/f_AB_i/f_AB_j arrays, no extra surrogate evaluations); response `{sobol:{inputVar:{main,total}}, sobolSecondOrder:{varA:{varB:float}}}` covers ∀ 3 orders simultaneously (⊥ opt-in; free since same batch); `numSamples` rounded up to next power-of-2 before sampling (Sobol' QMC requirement); response indices ⊥ validated non-negative/bounded (small-N MC noise yields small negative estimates, only `isfinite` enforced) (#470, #485)
V33: `_dak_exec_static` ! read back captured `./stdout`/`./stderr` on both the success AND failure path of `study.execute()` AND `dakenv.study(...)` construction (NIDR input-file parsing happens at construction, before `.execute()`); on failure, wrap Dakota's own exception in a `RuntimeError` whose message embeds the captured stdout+stderr, so callers/API error responses surface Dakota's real diagnostic text (e.g. the NIDR/input-file line that triggered an abort) instead of only Dakota's generic top-level exception ("Dakota aborted: Unknown error 254") (closes B16, B17)
V34: `SobolIndicesRequest.seed` accepts `0` (`ge=0`, numpy/scipy RNGs accept 0, unlike Dakota's NIDR parser which required `seed ≥ 1`, B17) — the NIDR constraint no longer applies now that V32 has migrated off Dakota's `variance_based_decomp`
V35: Sobol' second-order (pairwise interaction) indices are ALWAYS computed alongside first/total (V32 scipy-based approach, same batch); `SobolIndicesRequest` has no `secondOrder` opt-in flag (never added); response always includes `sobolSecondOrder:{varA:{varB:float}}` symmetric ∀ unordered pairs, no self-pair (diagonal filled on frontend from first-order index); formula: closed-form Jansen/Saltelli estimator reusing the same f_A/f_B/f_AB sample evaluations (Saltelli et al. 2010), validated vs Ishigami analytical reference (R1) via `test_sobol_indices_ishigami_analytical`
V36: Sobol' base sample count is a fixed module constant `SOBOL_BASE_SAMPLES=1024` (`dakota/funs_evaluate.py`), NOT the request's `numSamples` field (that field stays on `SobolIndicesRequest` only for schema compat w/ `ManualUQPropagationRequest`, shared by Histogram/Correlation, and is ignored by `evaluate_sobol_indices`); rationale: Sobol' cost is multiplicative `SOBOL_BASE_SAMPLES*(d_varying+2)` (Saltelli scheme) unlike the other UQ views' additive cost, so reusing the shared UQ default (10,000→16,384 rounded) would multiply out to 5-10x more surrogate evaluations than needed; N=1024 matches common SALib/scipy tutorial defaults for reliable index estimates at typical dimensionalities
V37: first-order/total-order Sobol' indices ship w/ bootstrap confidence intervals (`main_ci_low`,`main_ci_high`,`total_ci_low`,`total_ci_high` per input var, 95% CI, `SOBOL_BOOTSTRAP_RESAMPLES=1000` resamples) computed by resampling the ALREADY-computed f_A/f_B/f_AB evaluations (row-index resampling w/ replacement) — no extra `evaluate_sumo()` calls, effectively free; d_varying≥2 uses scipy's native `SobolResult.bootstrap()`; d_varying==1 uses a hand-rolled percentile bootstrap (same closed-form S1/ST formulas as the point estimate) since scipy's `sobol_indices()` cannot be called directly at d=1 (pre-existing squeeze bug, V32); second-order heatmap explicitly EXCLUDED from CI display (user decision, out of scope for now)
V38: `load_data()`'s `.dat`/`.txt` branch (`funs_data_processing.py`) validates EVERY data row's whitespace-token count against the header's BEFORE constructing the DataFrame; a mismatch raises `ValueError` naming the file, header column count, offending line number, and that line's column count/content — ⊥ let pandas' generic `"X columns passed, passed data had Y columns"` (no file/line context) bubble up uncaught (closes B20); `evaluate_sumo_manual_crossvalidation` additionally wraps its per-fold `get_results(predictions.dat)` call, prefixing any parse failure with `"Fold {N} of {N_CROSS_VALIDATION}: ..."` so a malformed-file error names which CV fold produced it
